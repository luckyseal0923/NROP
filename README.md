班別填報、床位動態、人力與特殊單位統計。此版本已從任意密碼的本機展示改為 Supabase Auth 與共享資料庫。

## 密碼重設信繁體中文範本（2026-10-27，NROP-20261027-05）

依使用者確認文案新增 [重設信範本](public/auth-emails/recovery.html)，主旨為「【NROP 護理即時動態平台】重設密碼通知」，包含「本信件僅供系統通知使用，請勿直接回覆。」並移除目前網站沒有對應輸入欄位的六碼驗證碼。唯一按鈕仍使用 Auth 的 `{{ .ConfirmationURL }}`，不寫入任何實際使用者連結。

範本由網站 `/auth-emails/recovery.html` 提供，Vite 建置會原樣複製；Dockerfile 同時加入 public 目錄。自架 Auth 已有來源變數對應，需將 `MAILER_SUBJECTS_RECOVERY` 與 `MAILER_TEMPLATES_RECOVERY` 設為確認的主旨及 `https://nrop.wfhai.org/auth-emails/recovery.html`，再重啟套用。發布及設定驗證另行記錄；未變更寄件地址、SMTP 憑證、其他信件類型、密碼或資料庫。完整前後內容見 [重設信範本修改對照](docs/密碼重設信範本_修改對照.md)。

## 帳號與權限

| 角色 | 功能 |
| --- | --- |
| 平台使用者 | 僅讀寫核准單位的填報資料 |
| 一般管理者 | 全院儀表板、選擇各單位填報、設定首次啟用的期初住院人數 |
| 系統管理者 | 一般管理者功能、帳號審核／啟用／停用、角色與單位指定、申請開關、操作紀錄、有效病床數管理（每次調整須重新驗證本人帳密） |

登入採 Email＋密碼。流程為「申請 → 待審核 → 系統管理者核准啟用」，註冊不要求收驗證信。Supabase Auth 負責密碼驗證；NROP 不儲存明碼、不提供查看他人密碼的功能。預設申請角色固定為平台使用者、狀態待審核；登入頁沒有角色選單。網頁的密碼規則為至少 6 碼並包含英文與數字，Auth 服務端也需依安裝指南設定密碼政策。

申請單位包含護理部及原有 28 個填報單位。護理部是行政申請單位，由系統管理者核准適當角色；不增加床數或班別填報。

**已安裝環境**：先備份並暫停填報，在 SQL Editor 執行 [UPGRADE_005_007.sql](supabase/UPGRADE_005_007.sql)，再部署本次網站程式。包含護理部、人工審核及單一資料區整併；不需重跑 INSTALL，遇到重複紀錄／期初衝突會停止而不覆蓋。請依 [單一資料區更新指南](docs/單一資料區_更新指南.md) 操作。註冊仍使用 `ENABLE_EMAIL_AUTOCONFIRM=true`，NROP 資格由管理者核准。

權限由每次資料庫 RPC 檢查，即使已持有登入憑證，停用的 NROP 成員也不能讀寫。成員資格屬於 NROP，不會停用共用 Auth 中的其他平台帳號；但變更共用 Auth 密碼會影響其他使用同一身分的系統。

## 先安裝資料庫

完整步驟見 [Supabase 與帳號系統安裝指南](docs/Supabase與帳號系統_安裝指南.md)。

1. 在新測試 Supabase 的 SQL Editor 貼上整份 [INSTALL.sql](supabase/INSTALL.sql)，執行一次。內容包含結構、權限、28 單位設定、2026-08-01～2026-10-25 的 DEMO。
2. 依指南啟用 Auth 的自動確認 Email，啟動網站並申請自己的帳號；送出後等候 NROP 管理者核准。
3. 將 [003_bootstrap_admin.sql](supabase/003_bootstrap_admin.sql) 的 Email 換成自己的，貼入 SQL Editor 執行。只初始化第一位系統管理者，不包含任何密碼。
4. 登入後用「帳號管理」核准其餘申請。也可執行 [004_verify_install.sql](supabase/004_verify_install.sql) 核對安裝結果。

`INSTALL.sql` 整份在單一交易內；失敗時回滾。重跑已安裝的結構會拒絕建立同名 schema，不會自動刪除或重建資料。`002_demo_seed.sql` 可獨立重跑，遇到已存在的 DEMO 不覆蓋。

## 本機啟動

使用 Node.js 22 LTS（本機已在 Node 20.20 驗證；伺服器 Dockerfile 使用 22）。

```powershell
npm ci
npm run dev
```

開啟終端機顯示的 `http://127.0.0.1:5173`。此版本需要啟動網站服務，不能再直接雙擊 `index.html`。

專案根目錄 `.env.local` 使用既有名稱：

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://your-supabase.example.org
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-public-anon-key
```

也接受 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`。只有公開網址與公開 key 會被編入網頁；禁止使用 service_role / secret key / 資料庫密碼。Vite 設定會拒絕 service_role JWT 與 secret key。

```powershell
npm run db:check
npm test
npm run build
```

`db:check` 僅檢查 Auth 與 NROP 設定 API，不輸出 key、不建立使用者或修改資料。

## 資料儲存與 DEMO

- `nrop.units`：有效床數、單位類別、允許填報欄位。
- `nrop.application_units`：護理部及各填報單位的申請選項，共 29 個。
- `nrop.members`：帳號角色、核准單位、啟用狀態；密碼不在此表。
- `nrop.records`：日期／班別／單位／資料區的唯一紀錄，含版本及更新者。所有紀錄共用一個資料區；相同日期、班別、單位只有一筆。`is_sample` 僅保留匯入來源，供正式啟用前盤點，不影響顯示、儲存、統計或權限。
- `nrop.opening_balances`：第一班的期初人數。
- `nrop.settings`：是否開放申請及統計起始日期。
- `nrop.audit_log`：帳號、設定、填報與後續重算的操作紀錄。

資料表放在未公開的 `nrop` schema，全部啟用 RLS 並取消瀏覽器直接讀寫權限；預設拒絕。僅公開必要的 `public.nrop_*` RPC，以固定搜尋路徑、明確角色及單位檢查執行。**不需將 `nrop` 加入 Exposed schemas**，也不需前端 service_role。

畫面直接查詢同一份資料，沒有正式／DEMO 選單；可選 2026-08-01～2026-10-25 查看原範例，新增及修改也在同一處。登入仍預設今天，不會每天由瀏覽器產生範例數字。舊 DEMO 尚無本科／隔離或護理師／護佐分類者保留原合計並要求補分類，不推測拆分。

資料快取只在記憶體中。登入憑證保存在本分頁的 sessionStorage，營運紀錄不再寫入 localStorage。舊瀏覽器 `nursing-daily-records` 仍留在原處，**未刪除、未自動上傳**；其中若有人工作業資料，需另外備份、辨識及核對後再規劃匯入，不能將所有舊資料當成正式資料。

當班人數、分類住院合計、護理之家人力在資料庫重算。修改前班時依 N→D→E 順序更新連續的後續班別，遇缺班就停止；不以字母排序猜班別。版本衝突會拒絕覆寫，避免不同電腦互相蓋掉。後續已有正式紀錄時，不允許把其前班改回暫存。

正式啟用前先備份並執行 [範例盤點 SQL](supabase/008_sample_inventory.sql)。本次保留範例，清除步驟待確認保留資料與首班期初人數後執行；帳號與單位設定可保留。

## 網站版本與更新檢查

登入及登入後頁面共用頁尾「NROP-20261027-05」與「檢查更新」。版本名稱為 NROP-YYYYMMDD-NN，流水號固定兩碼，同日遞增，換日從 01 開始。滑鼠停在版號可查看臺灣時間的建置時間及識別碼。開啟頁面、每五分鐘、返回前景時檢查網站已部署的版本；前景事件最短間隔一分鐘，背景分頁暫停自動檢查，網路恢復後重試，也可隨時手動檢查。

有新版時顯示「重新整理以更新」，不自動重載。按鈕會在處理資料時阻擋更新；有未儲存的填報、帳號設定或可見申請／密碼表單內容時先確認，取消會保留目前畫面。填報暫存或正式送出成功後更新儲存基準。此提醒針對版本更新按鈕，不代表所有離頁或切換單位動作都有自動暫存。

發布名稱取自 package.json 的 nropRelease；之後每次準備發布新版程式，先執行 `npm run release:next`，依臺灣日期更新兩碼流水號，再建置／提交／部署。當日已達 99 會拒絕覆用。內部套件版號保留供相容舊版本檢查使用，畫面顯示上述日期名稱。每次建置自動產生同一組網站識別碼及 dist/version.json，因此相同名稱重新建置仍能提示更新。僅推 GitHub、未部署的程式不會被當成網站新版；本機開發模式標示「本機開發」並停用發布檢查。

版本檔只有內部版號、發布名稱、建置識別碼及時間，不需資料庫或 SQL。檢查使用不快取及獨立查詢參數；更新導航也附建置識別碼以避免沿用舊首頁。nginx.conf 已提供首頁／版本檔重新驗證規則，現有 Railpack 部署則需部署後核對實際主機回應。若另設 CDN 規則，不應強制快取首頁與 version.json。

## 有效病床數管理與日期母數

系統管理者有「床數管理」頁籤，各單位以卡片顯示目前床數及下一筆排定設定。按該卡片「調整」才開啟固定單位的彈框，內含生效日期、新床數、選填原因、本單位近期調整紀錄與依日期排列的床數設定沿革。近期操作紀錄從現有 API 的全院最近 100 筆篩選；達載入上限時明確註記，較早的生效設定仍由完整床數沿革呈現。主頁不再放調整表單或全院歷史表格。

在彈框核對內容後，再輸入目前管理者本人的 Email 與密碼完成第二次確認；每次操作皆需重新驗證。取消帳密確認返回原調整內容，關閉調整彈框則清除未送出內容。畫面提醒「更改病床數將影響計算母數，請確認調整內容是否正確」。

僅可指定今天或未來日期，生效日 N／D／E 一起套用，直到下一筆設定生效；生效日前仍使用原母數。填報卡片、空床、超床、占床率、全院總床數、護理之家獨立床數、異常與 CSV 均依所選日期讀取。0 床時占床率顯示「—」，不以 0% 表示無法計算的比率。既有住院／異動／人力紀錄不重寫。全院母數仍只加總一般病房與特殊住院單位，其餘保留原有參考／獨立統計用途。

**床數管理初次啟用**：先備份，在 Supabase SQL Editor 執行整份 [UPGRADE_009.sql](supabase/UPGRADE_009.sql)，再重新整理網站；可重跑，不要重跑 INSTALL。已有 005–007 的環境直接執行 009 即可。未升級時原填報可繼續使用，床數管理顯示未啟用提示。首次安裝則使用新的 INSTALL.sql（已含 009）。**本次卡片／彈框更新沒有新增 SQL，已完成 009 不需重跑。** 詳見 [床數管理升級與驗收指南](docs/床數管理_升級與驗收指南.md)。

後端使用綁定管理者、單位、日期、床數與版本的確認請求。重新輸入密碼後建立獨立且僅存記憶體的 Auth 工作階段，資料庫核對已驗章的 password 驗證與真實 Auth session 建立時間；刷新舊憑證不能替代，不能重用同一驗證改另一筆。每次成功調整記錄臺灣可顯示的修改時間、操作者、前後床數、生效日及原因，主工作階段不切換帳號，密碼不送入資料庫 RPC 或保存於設定表。

**驗證界線**：61 項測試與建置通過；真實 Chrome 版面檢查使用合成資料，包含桌面／窄螢幕、卡片進入與取消帳密返回，沒有登入或修改真實床數。依使用者要求同步 GitHub；正式環境的帳密確認仍由管理者本人驗收。本次完整程式對照見 [床數卡片與調整彈框修改對照](docs/床數卡片與調整彈框_修改對照.md)，原資料庫功能見 [前版修改對照](docs/床數管理與版本命名_修改對照.md)。
