# 床數管理：升級與驗收指南

目前發布名稱為 NROP-20261027-02，床數管理使用單位卡片及調整彈框。僅系統管理者可使用；一般管理者與平台使用者不提供此頁籤，後端也拒絕其管理操作。本次介面更新不新增 SQL，已執行過 009 不需重跑；以下升級步驟適用尚未啟用床數管理的環境。

## 既有 Supabase 升級

1. 先做資料庫備份。這份更新以已安裝 005–007 的 NROP 為基礎。
2. 在 Supabase Studio 左側開啟 SQL Editor，建立新查詢。
3. 開啟專案的 `supabase/UPGRADE_009.sql`，複製整份內容貼入查詢並執行。檔案含 begin/commit，失敗會回滾；成功後可重跑，不覆蓋已調整的床數，不重建帳號，不重寫既有填報。不要重跑 INSTALL.sql。
4. 執行 `supabase/010_verify_bed_capacity.sql` 唯讀核對。首次應有 28 個原床數基準、管理功能 true、直接寫入權限 false；Auth 工作階段欄位可用。正式 Supabase Auth 必須保有標準 auth.sessions 的 id/user_id/created_at/not_after 欄位。
5. GitHub 程式由既有 Coolify Webhook 部署後，重新整理網站，頁尾確認日期版本名稱。以系統管理者登入，在上方選「床數管理」。未升級 SQL 時，原填報沿用既有方式，管理頁只顯示尚未啟用提示。

首次安裝的新環境使用新版 INSTALL.sql，已包含此結構；不需另外執行 009。SQL Editor 的資料庫管理密碼與網站帳號密碼不同，不需要把任何密碼貼進 SQL 或對話。

## 操作方式

主頁顯示全院有效床數及 28 個單位卡片，分成一般病房、特殊住院單位、其他單位。每張卡片顯示目前床數與最近一筆已排定設定，按「調整」才開啟該單位彈框。彈框固定選定單位，包含調整欄位、過去調整紀錄與完整生效設定沿革；手機版可向下捲動查看。一般病房、特殊住院單位計入全院母數；其他單位保留原參考床數或獨立統計方式。

生效日期可選今天或未來日期；同一日期的 N/D/E 都使用新母數，不分班別。生效日前使用原設定，已排定更晚的變更依該日期接續套用。床數可填 0–9999 的整數；沒有有效床數時占床率顯示「—」。

按「核對並驗證帳號密碼」，確認摘要中的單位、原值、新值、生效日期與選填原因。視窗會提醒：**更改病床數將影響計算母數，請確認調整內容是否正確。**

重新輸入目前登入系統管理者本人的 Email 和密碼、勾選內容正確，再按「驗證並儲存床數」。取消或密碼錯誤不會套用調整，密碼輸入欄會清空。確認請求有效時間五分鐘；其他管理者先變更相同單位時，版本衝突會阻擋覆蓋，須重新整理核對。

每次調整都需重新輸入帳密，不能使用另一位管理者的帳號，也不能只刷新原登入憑證。密碼只交給 Supabase Auth；床數 RPC 不接收或保存密碼。驗證工作階段不寫入瀏覽器持久儲存，不切換主畫面帳號，結束時只登出此次確認用的工作階段。

在該單位彈框的「過去調整紀錄」查看生效日期、原值→新值、修改時間、操作者及原因。近期紀錄從現有 API 的全院最近 100 筆篩選；達載入上限會明確註記，不能把這份近期清單當成全部稽核紀錄。下方「床數設定沿革」保留全部生效日期的設定，含原始基準與未來排定；同日多次修正的細節仍以稽核紀錄為準。時間以臺灣時區顯示，資料庫以 timestamptz 保存。

取消帳密確認會返回原調整彈框，保留尚未送出的日期與床數；關閉調整彈框或按「取消調整」會放棄未送出內容，再開其他單位不會殘留上一單位的欄位或歷史紀錄。

## 驗收與界線

本機已有 61 項測試通過，包含 PGlite 真實 PostgreSQL 引擎的授權／確認／衝突／歷史母數、前端三班／管理頁與隔離 Auth，以及卡片／彈框／單位歷史隔離／文字安全轉義測試；正式版建置通過。Chrome 桌面與窄螢幕檢查使用合成資料，不代表正式 Auth 或線上資料庫已驗收。未透過代理操作真實密碼或線上病床變更。

建議先在測試環境由管理者本人驗證一筆明確的測試單位與日期：確認非管理者無法開啟、錯誤密碼不會成功、取消不會成功、正確密碼才儲存；檢查生效日前後的三班、占床率、全院總床數及 CSV，並核對操作紀錄。不要為驗收任意改動正式單位床數。

如回應逾時而不確定是否已儲存，先重新整理床數與紀錄再重試。升級 SQL 沒有回復舊床數的自動刪除功能；錯誤的未來排定值可用相同生效日期重新驗證並修正，修改紀錄仍保留。

## 發布版本命名

畫面使用 `NROP-YYYYMMDD-NN`，例如 NROP-20261027-01。`package.json` 的 `nropRelease` 是已確定的發布名稱，不因重建同一版本自動跳號；每次準備發布新的程式修改，執行 `npm run release:next`，按臺灣日期遞增兩碼流水號。同日從 01 到 99，換日回到 01。之後建置、提交、推送 main，再確認部署結果。

原內部語意版號欄位保留供舊頁面的版本檢查相容，使用者介面改顯示日期版本。每次建置仍產生唯一 buildId，因此即使名稱相同，已開啟的頁面也能偵測重新建置。

實作對照官方文件：[Supabase 密碼登入](https://supabase.com/docs/reference/javascript/auth-signinwithpassword)、[JWT](https://supabase.com/docs/guides/auth/jwts)、[Auth 工作階段原始碼](https://github.com/supabase/auth/blob/v2.186.0/internal/models/sessions.go)。內建 reauthenticate 使用寄送 OTP 的方式，本次依需求使用重新輸入帳密的獨立登入驗證。
